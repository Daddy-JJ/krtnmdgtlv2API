# Mail queue: cron, locking, and reset coalescing

## Contract and boundaries

Password-reset requests enqueue work; they do not wait for SMTP. With the hosting
minimum schedule of `*/6 * * * *`, a new job normally waits up to roughly six
minutes before processing, plus queue, worker, retry, and transport delays. This
is not a six-minute delivery guarantee. `sent` means SMTP accepted the message,
not that it reached the inbox.

The worker now takes a database-specific MariaDB/MySQL named lock before stale
job recovery or processing. An overlapping invocation logs
`Mail worker already running; skipped.` and exits successfully. The lock uses a
dedicated connection in a separate one-connection pool, so it does not consume
the last connection of the work pool when `DB_CONNECTION_LIMIT=1`. Allow one
additional database connection per invocation; this does not change the hosting
process limit or start a daemon.

The worker checks ownership before each job and immediately before SMTP for
reset, Resume, and template-test mail. Losing the lock stops further work. The
lock connection is always closed, including on errors. A crashed connection's
lock is released by the database once disconnection is detected. Existing
`mail_outbox` jobs stuck in `processing` are recovered after ten minutes by a
later lock-owning invocation. Template-test jobs use a separate table and are
not covered by that recovery; interrupted tests need operator review.

SMTP cannot provide exactly-once delivery: acceptance followed by a crash before
the database records `sent` can still cause a retry. A send already in progress
cannot be canceled by a later loss of the lock.

## Reset request coalescing

- The recipient's `users` row is locked in the existing transaction before
  checking pending work.
- If the same user and destination already have an `auth.password-reset` job in
  `queued` or `processing`, the request reuses that pending work without writing
  another job. This includes jobs waiting for retry backoff.
- The pending job's original schedule, attempts, priority, template version, and
  payload are not reset. No reset token is generated by this duplicate request.
- Reset tokens are generated by the worker when processing, with the existing
  30-minute validity and fragment URL; time spent merely queued does not consume
  that token lifetime.
- A new request after a terminal job (`sent` or `failed`) remains possible,
  subject to existing rate limits. This is not a server-enforced six-minute
  cooldown after delivery.
- Admin retry uses the same user-lock ordering and rejects a reset retry beside
  pending work with existing HTTP 409 `MAIL_RETRY_NOT_ALLOWED`. A changed or
  inactive recipient is also rejected. RBAC/CSRF requirements remain unchanged.
- Historical duplicate jobs are not silently deleted, and no migration or seed
  is required. Review an existing backlog before enabling the updated worker.

The public `POST /api/v1/auth/forgot-password` success contract is unchanged for
known, unknown, and coalesced requests:

```json
{"success":true,"message":"If the address is valid, reset instructions will be sent.","data":null}
```

HTTP 200 does not reveal whether an account or pending job exists. Existing
validation (422) and rate limiting (429) remain in effect, including limits on
repeated requests that would otherwise be coalesced. No collection regeneration
is needed for this internal behavior change.
